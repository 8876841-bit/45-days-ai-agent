## Day 1：Token、Embedding 与 LLM 全景

第一天我主要建立了一个基础认知：大模型不是直接“读懂”人类文字，而是先把文字切成 token。我们平时看到的是一句完整的话，比如“我要在45天内掌握 AI Agent”，但模型真正处理的是 tokenizer 切出来的一段段 token。这些 token 可能是一个中文词、一个单字、一个英文片段，也可能是标点、空格、换行或代码符号。

token 被切出来以后，还会被转换成 token id。这个 id 本身只是编号，模型还不能直接用它理解语义。接下来 embedding 层会把 token id 变成向量。向量可以理解成模型内部使用的数字坐标。模型不是在中文或英文层面理解世界，而是在高维数字空间里处理这些向量。

第一天我还把 LLM 的完整链路串了一遍：文本先经过 tokenizer 变成 token，token 变成 id，id 经过 embedding 变成向量，向量进入 Transformer，通过 attention 结合上下文，最后模型输出下一个 token 的概率分布，再通过采样生成最终文字。

这一天最重要的理解是：大模型不是一次性写出完整答案，而是在不断预测下一个最可能的 token。它看起来像在说话，本质上是在根据上下文做连续预测。这个认知后面会影响我理解 prompt 成本、上下文窗口、RAG 和 Agent 记忆机制。

保留结论：LLM 的第一层逻辑，是围绕 token 展开的预测系统。

## Day 2：Self-Attention 与 QKV

第二天我学习了 self-attention。刚开始看到公式 `Attention(Q, K, V) = softmax(QK^T / sqrt(d_k))V` 会觉得很抽象，但拆开以后，其实可以先理解成三个问题：像不像、看多少、混合成什么。

在实验里，我用“我、喜欢、AI”三个 token 做演示。每个 token 都被人为设置成一个小向量。真实模型里的向量是训练出来的，但实验里的向量是人为设计的，目的是让“我”和“喜欢”更像，“AI”和前两个更不一样。这样就能观察 attention 权重如何变化。

attention scores 是原始相似度分数。它用 Q 和 K 做点积，再除以 `sqrt(d_k)` 缩放。可以先粗略理解成：当前 token 和其他 token 有多相关。scores 经过 softmax 以后，会变成 attention weights。weights 的每一行加起来约等于 1，表示当前 token 在更新自己时，分别应该看其他 token 多少。

最后一步是 `weights @ V`。这一步会把其他 token 的信息按比例混合进当前 token，形成新的表示。所以经过 attention 以后，一个 token 不再只是孤立的自己，而是带上了上下文信息。

这一天最重要的句子是：scores 是“像不像”，weights 是“看多少”，output 是“混合后的新表示”。这句话让我第一次真正理解了 self-attention 的直觉。

## Day 3：PyTorch、Shape 与 Mini Transformer 骨架

第三天我开始从 NumPy 过渡到 PyTorch。前一天我已经知道 attention 在数学上大概做什么，但第三天的重点是理解这些东西在代码里怎么流动，尤其是 tensor 的 shape。

我学到了三个核心维度：batch、seq、hidden。batch 表示一次处理多少条样本，seq 表示每条样本有多少个 token，hidden 表示每个 token 用多少维向量表示。比如输入 shape 是 `[batch, seq]`，它通常代表一批 token id。经过 embedding 以后，会变成 `[batch, seq, hidden]`，也就是每个 token id 都变成了一个向量。

接下来，模型会用 Linear 层把 embedding 后的向量投影成 Q、K、V。真实 Transformer 里，Q、K、V 不是凭空来的，而是由输入向量分别乘上可学习矩阵得到的。也就是 `Q = XWq`，`K = XWk`，`V = XWv`。

第三天还接触了 multi-head attention。可以先把它理解成：模型不是只用一套注意力看上下文，而是把 hidden 拆成多个 head，从多个角度观察上下文。代码里常见的 shape 会从 `[batch, seq, hidden]` 变成 `[batch, heads, seq, head_dim]`。

这一天的核心不是训练模型，而是不要在 shape 里迷路。只要能解释 batch、seq、hidden、heads、head_dim 的关系，后面看 Transformer 代码就会轻松很多。

## Day 4：最小字符级语言模型

第四天我开始训练一个最小字符级语言模型。这个模型很小，不是像 ChatGPT 那种大模型，但它做的任务和语言模型的底层目标是相通的：根据前面的内容预测下一个字符或 token。

如果训练文本是 `hello world`，模型看到 `hell` 时，要学会预测下一个字符可能是 `o`。在真实大语言模型里，预测的不是字符，而是 token。但核心思想是一样的：看前文，预测下一个最合适的单位。

这一天我第一次比较完整地理解训练循环。训练过程不是模型一下子就会了，而是不断重复：输入一段文本，模型做预测，把预测结果和正确答案对比，计算 loss，再根据 loss 反向传播调整参数。loss 可以理解成模型的错题分数，loss 越高说明错得越离谱，loss 慢慢下降说明模型正在学到文本规律。

这个实验让我第一次感受到，模型不是靠人工写规则来理解语言，而是通过大量预测任务学到统计规律。一开始模型生成的内容可能很乱，但训练一段时间以后，它会开始模仿训练文本里的模式。

Day 4 的关键理解是：语言模型的基础训练任务，就是 next token prediction。后面无论是聊天、写代码还是做 Agent，都建立在这个基础能力之上。

## Day 5：残差连接与 LayerNorm

第五天我学习了残差连接。刚开始看到 `output = x + f(x)`，感觉它非常简单，甚至有点奇怪。既然模型已经对输入做了加工，为什么还要把原来的 x 加回来？

后来我理解到，残差连接不是让模型偷懒，而是给信息和梯度留一条更顺的通路。如果没有残差连接，深层网络一层一层处理下去，原始信息可能被不断扭曲，训练时梯度也可能越来越弱。残差连接相当于每一层都保留一份原始输入，让模型在原来的基础上做修正。

一个很有帮助的理解是：普通网络像是在学习完整答案，而残差网络更像是在学习“需要改哪里”。模型不必从零生成一个全新的表示，只需要学习在原表示上增加什么变化。

在 Transformer 里，残差连接非常常见。attention 后面会有残差，FFN 后面也会有残差。可以粗略理解为：`x = x + attention(x)`，然后 `x = x + ffn(x)`。每一步都不是推翻之前的表示，而是在原表示上补充新信息。

LayerNorm 则帮助数值保持稳定。残差连接负责信息通路，LayerNorm 负责让每层输入输出分布更稳定。Day 5 的核心理解是：深度模型能堆很多层，不只是 attention 强，也因为残差连接和归一化让训练更稳定。

## Day 6：Tokenizer、Token 成本与上下文窗口

第六天我重新回到 tokenizer，但这次关注的不只是“文本如何切分”，而是 token 如何影响成本、速度和上下文长度。

我通过对比中文、英文、代码和 Markdown 的 token 数，意识到模型处理的不是我们看到的字符数，而是 tokenizer 切出来的 token 数。同样一句话，不同语言和格式可能会产生不同数量的 token。代码里的缩进、换行、括号、引号也都会占 token。

token 数直接影响三个方面。第一是成本，很多模型按输入输出 token 数计费。第二是速度，token 越多，模型处理上下文越慢。第三是上下文窗口压力，模型一次能看到的 token 数有限，如果上下文太长，旧信息可能被截断，或者必须摘要和压缩。

这一天我还理解了上下文窗口。它可以理解成模型一次请求时能看到的工作台。system prompt、用户输入、历史消息、工具返回结果、RAG 检索内容，全部都要放在这个工作台里。工作台不是无限大的，所以 Agent 不能把所有东西原样塞给模型。

Day 6 的关键理解是：token 是大模型世界里的预算单位。一个好的 Agent 必须管理上下文，而不是无限追加内容。

## Day 7：Embedding 与语义检索

第七天我学习了 embedding 和语义检索。之前我已经知道 token 会被变成向量，但今天进一步理解到，向量不仅可以给模型内部计算使用，也可以拿来做搜索。

传统搜索更依赖关键词。比如搜索“AI Agent”，系统可能主要找包含这些字面词的内容。但语义检索不只看字面匹配，而是看两段话的意思是否接近。比如“怎么让 AI 调用工具”和“如何实现 function calling”，字面不同，但语义相近。如果它们变成 embedding 后，向量方向接近，系统就能认为它们相关。

Embedding 可以理解成把文本放进一个语义地图里。意思相近的文本，在这个地图里的位置更近；意思不相关的文本，距离更远。判断距离时可以用 cosine similarity，也就是看两个向量方向是否接近。

这一天也把 embedding 和 RAG 联系起来。RAG 的流程是：先把文档切成 chunk，再给每个 chunk 生成 embedding。用户提问时，也把问题变成 embedding，然后在向量库里找最相近的 chunk。最后把这些相关内容放进上下文，让模型基于资料回答。

Day 7 的关键理解是：RAG 不是让模型记住所有文档，而是先找相关资料，再让模型回答。

## Day 8：KV Cache 与长上下文成本

第八天我学习了 KV Cache。刚开始看到这个词时会觉得陌生，但把它和 Day 2 的 Q、K、V 联系起来，就清楚很多。

在 attention 里，每个 token 都会生成 Q、K、V。Q 是“我在找什么”，K 是“我有什么标签”，V 是“我的实际内容”。模型生成回答时，不是一次性写完整段，而是一个 token 一个 token 往后生成。

如果每生成一个新 token，都重新计算前面所有 token 的 K 和 V，那会非常浪费。因为前面 token 的 K 和 V 已经算过了，没必要每次都重算。KV Cache 的作用就是把前面 token 的 K 和 V 缓存起来，后面生成新 token 时直接复用。

这一天我还理解了 prefill 和 decode。prefill 是模型先读完整个输入，把上下文处理一遍。decode 是模型开始逐个生成输出 token。KV Cache 主要在 decode 阶段发挥作用，让生成更快。

但 KV Cache 不是免费午餐。上下文越长，需要缓存的 K 和 V 越多，也会占用更多内存和显存。所以长上下文依然有成本。Agent 不能因为模型支持长上下文，就随便塞所有历史记录。

Day 8 的关键理解是：KV Cache 可以减少重复计算，但不能消除长上下文的成本。

## Day 9：采样策略

第九天我学习了采样策略，也就是模型算出下一个 token 的概率分布以后，到底怎么选最终输出。

以前我以为模型总是选概率最高的 token。但今天发现，如果永远选最高概率，输出会很稳定，但也可能很死板；如果允许模型从多个候选中采样，输出会更灵活，但也可能更发散。

temperature 可以理解成模型的大胆程度。temperature 低时，模型更保守，更倾向于选择概率最高的 token。temperature 高时，模型更开放，会给低概率 token 更多机会。对于分类、抽取、代码修复这类需要稳定的任务，temperature 通常应该低一点。对于文案、故事、创意发散，可以适当高一点。

top-k 表示只从概率最高的前 k 个 token 里选。top-p 表示从累计概率达到某个阈值的一组 token 里选。top-p 比 top-k 更灵活，因为候选集合会根据概率分布自动变化。

Day 9 的关键理解是：模型不是只有一个答案，它是在概率分布里做选择。采样策略决定了输出是稳定、保守，还是多样、发散。

## Day 10：第一阶段复盘

第十天我做第一阶段复盘，没有继续学习新概念，而是把前九天的底层知识串起来。

这十天我逐渐把大模型从一个模糊黑盒，拆成了一条相对清楚的链路：文本被 tokenizer 切成 token，token 变成 id，id 经过 embedding 变成向量，向量进入 Transformer，通过 attention 结合上下文，残差连接和 LayerNorm 让深层网络更稳定，模型输出下一个 token 的概率分布，再通过采样策略选择最终 token。

我也意识到，前十天不是为了成为大模型研究员，而是为了后面做 Agent 时有底层判断力。如果不知道 token，就很难理解为什么 prompt 太长会贵。如果不知道上下文窗口，就很难理解为什么历史消息不能无限塞。如果不知道 embedding，就很难理解 RAG 为什么要先检索。如果不知道采样策略，就很难控制模型输出风格。

第十天的核心收获是：大模型不是魔法，而是一套围绕 token 展开的预测系统。它的能力很强，但也有明确边界。Agent 工程需要建立在理解这些边界之上。

第一阶段结束后，我准备进入第二阶段：Agent 核心机制。也就是开始学习 messages、system prompt、tool use、RAG、ReAct、memory 和 eval。

## Day 11：Messages 与 API Payload

第十一天我正式进入 Agent 核心机制。今天学的第一个概念是 messages 数组。

以前我以为调用模型就是把一句用户问题发过去，然后模型返回一句回答。但真实 API 调用中，模型看到的不是单独一句话，而是一组 messages。每条 message 都有一个 role，常见的 role 包括 system、user、assistant 和 tool。

system message 可以理解成最高优先级的长期规则，用来告诉模型它是谁、要遵守什么限制、应该用什么格式回答。user message 是用户这次说的话。assistant message 是模型之前的回复。tool message 是工具执行后返回给模型的结果。

这让我理解了一个重要点：Agent 的“记忆感”很多时候不是模型真的记住了，而是我们把历史 messages 一起发给了它。如果历史消息还在上下文里，模型就能参考；如果被截断了，模型就像忘了一样。

Day 11 的关键理解是：Agent 首先是一种消息组织方式。你怎么组织 messages，模型就怎么理解当前任务。清晰的 role、历史、工具结果和输出约束，会让 Agent 更稳定。

## Day 12：上下文管理

第十二天我学习上下文管理。Day 11 我已经知道模型看到的是 messages 数组，但今天进一步理解到：messages 不能无限增长。

一开始我以为，要让 Agent 记住用户说过的话，只要把所有历史对话一直追加到 messages 里就行。但这样会带来明显问题。第一，token 越来越多，成本越来越高。第二，模型处理速度变慢。第三，上下文窗口有限，重要信息可能被挤掉。

所以 Agent 必须做上下文管理。常见策略包括截断、摘要、滑动窗口和长期记忆。截断最简单，只保留最近几轮对话，但可能丢掉早期重要信息。摘要可以压缩旧对话，但摘要质量会影响后续表现。滑动窗口适合普通连续对话。长期记忆则适合保存稳定偏好、重要事实和可检索知识。

我还意识到，工具返回结果也需要管理。如果工具返回一大段网页、日志或搜索结果，不能原样全部塞给模型，而应该筛选、压缩、摘要后再放进上下文。

Day 12 的关键理解是：好的 Agent 不是记得越多越好，而是知道什么时候该记、什么时候该忘、什么时候该检索。

## Day 13：System Prompt 工程

第十三天我学习 system prompt。以前我把 prompt 理解成一句普通指令，比如“帮我总结一下”。但今天我意识到，system prompt 更像 Agent 的底层行为规则。

user prompt 是这次具体要做什么，而 system prompt 更像是这个助手一直要遵守的原则。它可以定义角色、边界、输出格式、失败策略和禁止行为。比如告诉模型：你是一个严谨的代码助手，不要编造不存在的 API，输出必须是 JSON，不确定时要说明不确定。

这一天我最大的理解是：system prompt 不是写得越长越好，而是要减少歧义。一个好的 system prompt 应该明确三件事：模型扮演什么角色，必须遵守什么限制，最终应该用什么格式输出。

如果 system prompt 太模糊，模型会自由发挥。如果太啰嗦，又会浪费 token，还可能让重点变弱。所以 prompt 工程不是堆字数，而是用清楚、稳定、可测试的方式约束模型行为。

Day 13 的关键理解是：system prompt 是 Agent 的行为底盘，决定模型不是随便回答，而是按规则持续工作。

---

## Day 14：Few-Shot 与推理提示

第十四天我学习 few-shot 和推理提示。以前我更习惯给模型写规则，比如告诉它“请按这个格式输出”。今天我理解到，有时候给模型讲很多规则，不如直接给它几个例子。

Few-shot 的意思是在正式任务之前，先给模型几个输入和输出样例。模型会从样例中学习任务模式，包括格式、判断标准、语气和边界。比如做情绪分类时，与其只说“判断积极或消极”，不如给几个例子，让模型看到什么样的句子应该归为积极、消极或中性。

我还学到，推理提示不是所有任务都适合。对于复杂推理、规划或分析任务，可以引导模型先分析再回答。但对于简单抽取、格式化输出或分类任务，过多推理可能反而增加 token 和冗余。

这一天的关键理解是：模型很擅长模仿模式。规则告诉模型应该做什么，例子让模型看到具体怎么做。

Day 14 的结论是：few-shot 的本质，是用例子降低模型理解任务的成本。

## Day 15：Function Calling 入门

第十五天我学习 function calling，也就是工具调用。以前我以为 Agent 会自己查天气、发邮件、算数据。今天我理解到，模型本身并不会真的执行这些动作，它只是判断应该调用哪个工具，并生成结构化参数。

比如用户问“上海天气怎么样”，模型不会自己访问天气网站。它会输出一个工具调用请求，比如调用 `get_weather`，参数是 `city=上海`。真正执行工具的是我们的程序。

Function calling 里非常重要的是 schema。schema 要告诉模型工具叫什么、能做什么、需要哪些参数、参数类型是什么。如果 schema 描述不清楚，模型可能选错工具，或者传错参数。

这一天让我更清楚地理解 Agent 的行动能力来自哪里。Agent 不是模型自己会动手，而是模型负责判断，程序负责执行，执行结果再回到模型上下文，让模型继续推理或给出最终回答。

Day 15 的关键结论是：function calling 是让模型学会“提出工具调用”，不是让模型亲自执行工具。

## Day 16：Tool Runtime

第十六天我学习 tool runtime，也就是工具执行器。Day 15 我知道模型会提出工具调用，而 Day 16 重点是程序如何真正执行这个调用。

完整链路是：用户提出问题，模型判断需要工具，模型输出工具名和参数，程序检查参数，执行本地函数或外部 API，再把工具结果回传给模型，模型基于结果生成最终回答。

这条链路看起来简单，但工程细节很多。比如工具名不存在怎么办？参数缺失怎么办？参数类型不对怎么办？工具执行失败怎么办？返回结果太长怎么办？这些都不能只靠模型自己处理，程序必须兜底。

今天我理解到，Agent 的稳定性不只是靠模型聪明，还要靠工具执行器的设计。tool runtime 需要做工具注册、参数校验、错误捕获、结果压缩和格式统一。

Day 16 的关键结论是：tool runtime 是 Agent 从“会说”到“会做”的桥。模型负责选择工具，程序负责安全执行工具。

---

## Day 17：RAG 索引

第十七天我正式进入 RAG。前面学过 embedding，知道文本可以变成向量；今天开始把 embedding 用到文档检索里。

RAG 的第一步不是直接问模型，而是先整理资料库。我们需要把文档切成 chunk，然后给每个 chunk 生成 embedding，存进索引或向量库里。这样用户提问时，系统可以先根据问题找到最相关的文档片段。

这一天我理解到，chunk 切分会直接影响 RAG 效果。如果 chunk 太大，里面可能混进很多无关内容；如果 chunk 太小，语义可能不完整；如果没有重叠，关键信息可能刚好被切断。

所以 RAG 不是简单地“把文档塞给模型”，而是先把知识整理成可检索结构。它的第一步是知识预处理，而不是生成回答。

Day 17 的关键结论是：RAG 的第一步，是把资料变成能被检索的知识库。

---

## Day 18：RAG 问答链路

第十八天我把 RAG 索引和问答链路接起来。完整流程是：用户提问，问题变成 embedding，系统去索引里找最相关的 chunk，把这些 chunk 放进 prompt，模型基于这些资料回答。

这一天我更清楚地理解了 RAG 的本质：不是模型自己知道答案，而是先把相关资料找出来，再让模型阅读资料后回答。

同时我也意识到，RAG 不等于不会幻觉。如果检索错了，模型可能基于错误资料回答。如果资料不够，模型可能自己补充猜测。如果 prompt 没有限制，模型可能不引用来源。

所以 RAG 问答里很重要的是约束模型：只能基于检索片段回答，不知道就说不知道，必要时引用来源。检索质量决定了回答的上限，生成质量决定了最终表达。

Day 18 的关键结论是：RAG 是“先找资料，再生成回答”。检索错了，生成再强也可能错。

---

## Day 19：ReAct Loop

第十九天我学习 ReAct，也就是 Reasoning + Acting。它的核心是让 Agent 边思考边行动。

以前我理解 Agent，觉得它可能就是一次调用模型拿到答案。今天我发现，真正的 Agent 往往是一个循环。它会先思考下一步做什么，然后调用工具，观察工具结果，再继续思考下一步，直到可以给出最终答案。

这个循环可以拆成 Thought、Action、Observation。Thought 是模型的下一步判断，Action 是要执行的工具或动作，Observation 是工具返回结果。然后模型根据 Observation 再继续推理。

这让我理解到，Agent 的自主性不是魔法，而是循环机制。模型每一步只做一个小决策，程序执行动作并把结果放回上下文，多轮循环后就像 Agent 会自己推进任务。

但 ReAct 也需要边界。必须设置最大步数，处理工具失败，保证输出格式稳定，否则 Agent 可能陷入循环或解析失败。

Day 19 的关键结论是：Agent 的自主性来自模型决策、工具执行和观察反馈之间的循环。

---

## Day 20：Memory

第二十天我学习 Agent 的记忆机制。之前已经知道，模型的“记忆感”很多时候来自上下文里的 messages。但上下文窗口有限，不能无限保存所有历史。

所以 Agent 需要更明确的 memory 设计。短期记忆服务当前对话，比如最近几轮消息。长期记忆保存更稳定的信息，比如用户偏好、长期事实和重要约定。向量记忆适合保存大量历史片段或知识，需要时通过 embedding 检索回来。

这一天我最大的理解是：记忆不是越多越好。如果 Agent 什么都记，就会把临时信息当成长期事实。如果记忆不更新，就会保留过时信息。如果记忆没有筛选，就会污染上下文。

好的记忆机制应该有写入规则、读取规则、更新规则和删除规则。比如用户明确说“记住我喜欢简洁回答”时，可以写入长期偏好；但一次临时任务里的细节，不一定应该长期保存。

Day 20 的关键结论是：Agent 的记忆不是保存全部聊天记录，而是有选择地保留有长期价值的信息。

---

## Day 21：Agent Eval 初版

第二十一天我学习 Agent eval，也就是评估。以前判断 Agent 好不好，主要靠感觉：跑几个例子，觉得回答不错，就以为它能用了。但今天我意识到，这种方式不可靠。

Agent 需要固定测试用例。比如准备十个问题，每个问题都有预期行为。每次改 prompt、改工具或改代码，都重新跑一遍测试。这样才能知道改动是真的变好了，还是只是某个例子碰巧变好了。

Eval 可以记录很多指标：成功率、延迟、token 成本、工具调用是否正确、输出格式是否稳定、是否幻觉、失败类型是什么。

这一天我理解到，没有 eval，就很难做 Agent 工程。因为 Agent 的行为会受模型、prompt、工具、上下文和采样参数共同影响。只靠人工感觉，很容易漏掉问题。

Day 21 的关键结论是：eval 让 Agent 从“看起来能用”变成“可以被验证”。

---

## Day 22：个人助理 Agent v1 整合

第二十二天我做阶段二整合，把前面学到的 Agent 核心机制串成个人助理 Agent v1。

这一天我把 messages、context manager、system prompt、few-shot、tool use、RAG、ReAct、memory 和 eval 放到一个整体里看。单个概念学懂是一回事，把它们接成一个能运行的系统又是另一回事。

一个 Agent 不是只有模型。它有输入消息、上下文管理、工具注册、工具执行、知识检索、记忆机制和评估系统。每一块单独看都不算特别复杂，但组合起来就需要清楚的模块边界。

这一天我开始思考很多工程问题：工具结果在哪里压缩？记忆什么时候写入？RAG 结果放进 prompt 的哪一段？eval 只评估最终答案，还是也评估工具调用过程？

Day 22 的关键结论是：个人助理 Agent v1 的目标不是完美，而是先把模型、工具、知识和记忆接成一个完整闭环。

---

## Day 23：Orchestrator-Worker 架构

第二十三天我开始学习多 Agent 架构，第一种是 Orchestrator-Worker。

Orchestrator 可以理解成项目经理，负责理解目标、拆分任务、分配任务、汇总结果。Worker 像执行人员，每个 worker 负责一个更具体的子任务。比如一个负责查资料，一个负责编码，一个负责测试，一个负责总结。

这一天我理解到，多 Agent 不是为了显得高级，而是为了解决复杂任务的分工问题。如果任务简单，一个 Agent 就够了。如果任务复杂，需要多步骤、多角色、多种上下文，多 Agent 才可能有价值。

但多 Agent 也会增加成本。它会增加 token 消耗、延迟和协调复杂度。多个 Agent 之间传递信息时，也可能出现丢失或误解。

Day 23 的关键结论是：多 Agent 的价值来自合理分工，不来自 Agent 数量。不是能拆就拆，而是拆分收益要大于沟通成本。

---

## Day 24：Subagent 设计原则

第二十四天我继续学习 subagent 设计。重点不是怎么创建更多 Agent，而是什么时候真的应该创建 subagent。

适合创建 subagent 的情况包括：任务能清楚拆分，不同子任务需要不同上下文，需要权限隔离，或者可以并行执行。比如研究任务和代码修改任务可以拆开，因为它们需要的上下文和输出不同。

但如果任务本身很简单，强行拆成多个 Agent 反而会增加复杂度。每个 subagent 都需要输入、输出、上下文和协调方式。如果边界不清楚，多 Agent 系统会比单 Agent 更混乱。

这一天我理解到，subagent 不是角色扮演，而是工程边界。每个 subagent 都应该有明确职责和可验证输出。

Day 24 的关键结论是：创建 subagent 前，要先问它是否真的降低复杂度，而不是制造复杂度。

---

## Day 25：Skill Registry

第二十五天我学习 Skill Registry，也就是技能注册表。

如果工具是一个个具体能力，Skill Registry 就像一本能力目录。它告诉 Agent 系统里有哪些技能，每个技能能做什么，需要什么输入，会返回什么输出，失败时会怎样。

以前我可能只关注工具函数本身。但今天我意识到，对 Agent 来说，工具描述同样重要。因为模型要根据 name、description 和 schema 来判断该不该用这个技能。

如果技能描述含糊，模型就可能选错工具。如果输入输出不清楚，执行阶段就容易出错。所以 Skill Registry 的重点不是堆很多技能，而是让每个技能都能被模型正确理解和调用。

Day 25 的关键结论是：Skill Registry 是 Agent 的工具箱目录。技能不仅要存在，还要被描述清楚。

---

## Day 26：感知-推理-执行三层架构

第二十六天我学习感知、推理、执行三层架构。

这个架构让我对 Agent 产品化更清楚。感知层负责输入，比如用户消息、文件、网页、数据库和工具返回结果。推理层负责理解目标、拆分任务、选择工具和判断风险。执行层负责真正行动，比如调用 API、写文件、运行代码或发送请求。

以前我看 Agent，容易把所有东西混在一起。用三层结构拆开以后，就更容易定位问题。比如一个 Agent 出错，可以问：是输入没读对？是推理判断错了？还是执行工具失败了？

这一天我理解到，Agent 不是一团 prompt，而是一个系统。系统需要层次和边界，否则后面很难维护和扩展。

Day 26 的关键结论是：感知负责看见，推理负责决定，执行负责行动。

---

## Day 27：LangGraph 入门

第二十七天我开始学习 LangGraph。前面我手写过 ReAct loop，知道 Agent 可以通过循环推进任务。LangGraph 则把这个循环和分支变成图结构。

LangGraph 里有几个核心概念：state、node 和 edge。state 是当前任务的状态，node 是一个处理步骤，edge 决定步骤之间怎么流转。

这一天我理解到，LangGraph 的价值不是“框架高级”，而是让 Agent 流程更显式、更可控。手写 loop 时，流程可能藏在代码里。用 graph 后，可以清楚看到 planner、tool、answer 等步骤如何连接，什么时候走工具分支，什么时候直接回答。

它特别适合多步骤、可分支、需要追踪状态的 Agent。如果只是简单问答，可能不需要上框架。但如果有工具、记忆、检索和条件判断，graph 结构就会很有帮助。

Day 27 的关键结论是：LangGraph 用图来组织 Agent 的状态和流程。

---

## Day 28：LangGraph 重写个人助理

第二十八天我尝试用 LangGraph 重写个人助理 Agent。

这个过程让我意识到，框架不是为了替代思考，而是为了让结构更清楚。原来写在一个流程里的逻辑，可以拆成不同 node：memory node 读取记忆，RAG node 检索知识，tool node 执行工具，answer node 生成最终回答。

这些 node 之间通过 state 传递信息。state 让每一步都能知道当前任务已经有什么输入、检索到了什么、调用过什么工具、是否已经可以回答。

这一天我理解到，LangGraph 适合把隐含流程变成显式流程。复杂 Agent 最怕流程藏在代码深处，出了问题不知道是哪一步。graph 结构能让执行路径更容易观察和调试。

Day 28 的关键结论是：用 LangGraph 重写 Agent，本质是把 Agent 的状态流转和分支逻辑显式化。

---

## Day 29：Agent 框架对比

第二十九天我对比了几个 Agent 框架，比如 LangGraph、AutoGen 和 CrewAI。

以前看到这么多框架会焦虑，觉得是不是每个都要学。但今天我理解到，框架不是路线本身，而是工具。关键不是哪个框架更热门，而是它解决的问题是否适合当前任务。

LangGraph 更强调状态流转和流程控制，适合需要清晰步骤、条件分支和可追踪执行路径的 Agent。AutoGen 更强调多 Agent 对话协作，适合多个角色互相讨论和推进任务。CrewAI 更像角色分工式任务编排，适合用明确角色完成流程化任务。

这一天我最大的收获是：先理解任务复杂度，再选择框架。不要因为框架流行就使用，也不要为了用框架而设计复杂系统。

Day 29 的关键结论是：框架选择应该服务于任务，而不是反过来让任务迁就框架。

---

## Day 30：多 Agent 阶段复盘

第三十天我做多 Agent 阶段复盘。

从 Day 23 到 Day 29，我学习了 Orchestrator-Worker、subagent、Skill Registry、感知-推理-执行三层架构、LangGraph 和框架对比。

这一阶段让我把 Agent 从“一个聊天机器人”升级成“一个系统”来看。一个复杂 Agent 可能有规划者、执行者、工具、技能目录、状态流转、记忆和评估。

但我也更清楚地意识到，多 Agent 不是万能解法。它会增加 token 成本、延迟、协调成本和信息传递风险。如果一个单 Agent 能稳定完成任务，就不应该为了架构感强行拆分。

Day 30 的关键结论是：多 Agent 的核心不是数量，而是分工、边界和协作。架构的价值是降低复杂度，而不是制造复杂度。

## Day 31：AI 编程工具与工作流

第三十一天我开始进入垂直应用实战，第一站是 AI 编程工具。

我对比了 Claude Code、Cursor、Windsurf、Codex 这类工具。以前我把它们都理解成“AI 写代码”，但今天我发现，它们真正的差异在工作流。有的更适合编辑器内快速补全和修改，有的更适合理解整个代码库，有的更像任务代理，可以读文件、运行命令、修改项目。

这一天我理解到，AI 编程不是把代码全交给 AI，而是人和 AI 分工。人负责目标、边界、验收标准和最终判断。AI 负责生成方案、修改代码、解释逻辑、运行测试和加速迭代。

如果需求说不清楚，AI 很容易写偏。如果没有测试和验收标准，即使 AI 写出了代码，也不一定能用。

Day 31 的关键结论是：AI 编程工具的价值不只是生成代码，而是加速理解、实现和迭代。

## Day 32：Vibe Coding 方法论

第三十二天我学习 Vibe Coding。

这个词听起来很轻松，但真正做起来不是随便让 AI 写代码。我理解的 Vibe Coding，是人和 AI 小步协作的开发方式。人先说清楚要做什么，AI 实现一个版本，人检查结果，再让 AI 小步修改。

关键不是一次让 AI 做完所有东西，而是每次只推进一小步。每一步都要有明确目标和验收标准。比如不是说“做一个好看的页面”，而是说清楚布局、输入输出、交互、边界情况和完成标准。

这一天我还意识到，看不懂的代码不能跳过。要立刻让 AI 解释，否则项目越往后，自己越容易失控。

Day 32 的关键结论是：Vibe Coding 不是把方向交给 AI，而是人定方向，AI 加速实现，人持续校准。

## Day 33：毕业项目 PRD

第三十三天我开始确定毕业项目，并写 PRD。

前面学了很多概念和工具，但如果没有一个真实项目承载，很容易变成知识点堆积。PRD 的作用是把一个想法收敛成可以实现的范围。

我需要回答几个问题：这个项目给谁用？解决什么问题？最核心的功能是什么？哪些功能暂时不做？做到什么程度算完成？

这一天我理解到，项目不是越大越好，而是边界越清楚越好。如果一开始什么都想做，十天内很难完成。先收敛成一个 MVP，反而更容易交付。

MVP 不是低质量版本，而是最小可验证版本。它应该能跑通核心场景，让别人看懂项目价值。

Day 33 的关键结论是：毕业项目第一步不是写代码，而是把问题、用户和范围说清楚。

## Day 34：毕业项目架构

第三十四天我做毕业项目架构设计。

PRD 定义了要做什么，架构设计则回答怎么拆成可实现模块。我需要想清楚：用户输入从哪里来，Agent 怎么理解任务，需要哪些工具，是否需要 RAG，状态如何保存，失败时怎么处理，最终结果怎么返回。

这一天我理解到，架构图不是为了画得漂亮，而是为了降低实现时的混乱。如果不先设计，写代码时很容易想到哪写到哪，最后模块之间互相缠在一起，很难维护。

好的架构应该说明数据怎么流动，每个模块的输入输出是什么，哪些地方可能失败，失败后如何处理。

Day 34 的关键结论是：架构设计是把项目从一个想法，变成一组可实现、可调试、可扩展的模块。

## Day 35：毕业项目核心链路

第三十五天我开始写毕业项目核心链路。

这一阶段最重要的不是把所有功能做完，而是先跑通最短路径：用户输入，Agent 判断，调用工具或检索资料，生成结果，返回给用户。

这一天我理解到，先跑通闭环比一开始追求完美更重要。如果核心链路没通，界面再好看也没有意义。如果核心链路能跑，后面才有迭代基础。

真实项目里，很多问题不是理论问题，而是连接问题。比如配置读不到，参数传错，工具返回格式不对，异常没有处理。这些都需要一点点调通。

Day 35 的关键结论是：MVP 的第一目标，是让用户输入到最终输出这条路真正跑通。

## Day 36：CLI 或 Web UI

第三十六天我给项目加使用入口，可以是 CLI，也可以是 Web UI。

这一天我理解到，一个项目能运行，和别人能使用，是两回事。如果只能我自己在代码里改参数运行，那还只是实验。如果别人可以通过命令行或页面输入问题并看到结果，它才更像一个产品。

CLI 更快，适合开发和调试。Web UI 更适合展示，别人更容易理解。但无论哪种形式，最小交互闭环都很重要：用户能输入，系统能处理，结果能显示，错误能提示。

界面不是装饰，而是把 Agent 能力交给用户的入口。即使界面简单，也要让核心功能可用。

Day 36 的关键结论是：让项目能被别人使用，是从实验走向作品的重要一步。

## Day 37：日志与 Trace

第三十七天我给项目加日志和 trace。

以前跑 Agent 时，我只看最终回答。回答对了就觉得不错，回答错了就重试。但今天我意识到，这样没办法真正调试。Agent 的错误可能发生在很多地方：prompt 没写清楚，工具选错，工具返回异常，RAG 检索错，模型最后总结跑偏。

Trace 就像 Agent 的运行记录。它应该记录用户输入、模型决策、工具调用、工具结果、耗时、错误和最终输出。有了 trace，才能知道 Agent 每一步发生了什么。

这一天的核心理解是：没有 trace，Agent 就是黑盒。出了问题只能猜。有了 trace，才能定位到底是哪一步出错。

Day 37 的关键结论是：Trace 让 Agent 从黑盒变成可观察系统。

## Day 38：成本控制

第三十八天我学习成本控制。

前面已经知道 token 会影响费用，但今天把它放进项目里更有感觉。一次 Agent 运行，不只是用户输入那句话在花 token。system prompt、历史上下文、RAG 检索内容、工具返回结果、模型输出都会消耗 token。

这些加起来，才是一次任务的真实成本。如果 prompt 很长，成本会上升；检索 chunk 太多，成本会上升；工具返回一大段原始内容，成本也会上升；多 Agent 来回通信，成本更高。

这一天我理解到，Agent 的成本不是固定的，而是由流程设计决定的。成本控制不是最后才做，而是架构设计的一部分。

Day 38 的关键结论是：会做 Agent，不只是让它能回答，还要知道每次回答花了多少代价。

## Day 39：Prompt 版本管理

第三十九天我学习 prompt 版本管理。

以前改 prompt 很随意，觉得哪里不好就直接在代码里改一句。但今天我意识到，这样很容易失控。prompt 一改，Agent 行为可能就变了。一个任务变好，另一个任务可能变差。

所以 prompt 应该像代码一样被管理。把 prompt 从代码里抽离出来，保存成版本文件，比如 v1、v2、v3。每个版本记录改了什么、为什么改、效果如何。

Prompt 优化不能只靠感觉，还要结合 eval。每次改 prompt 后，用固定测试集对比效果，才能知道改动是否真的带来提升。

Day 39 的关键结论是：prompt 也是 Agent 系统的一部分，需要版本化、评估和回滚。

## Day 40：垂直应用阶段复盘

第四十天我做垂直应用阶段复盘。

从 Day 31 到 Day 40，我从 AI 编程工具和 Vibe Coding，逐步走到毕业项目 MVP。这个阶段让我意识到，真正做项目时，前面学过的知识点会自动连起来。

AI 编程工具加速实现，Vibe Coding 帮助小步迭代，PRD 收敛范围，架构图理清模块，日志和成本追踪帮助调试，eval 帮助判断质量。

这一天我最大的理解是：作品不是靠一天爆发做出来的，而是每天把一个小闭环往前推一点。项目不一定完美，但只要能运行、能演示、能解释，就已经从学习笔记变成作品雏形。

Day 40 的关键结论是：垂直应用阶段的重点，是把概念变成一个能展示的真实项目。

## Day 41：Eval 完善

第四十一天我继续完善 eval。

Day 21 的时候，我只是做了基础评估。今天把 eval 扩展到毕业项目里，不只是问几个简单问题，而是准备更多测试用例，包括正常情况、边界情况、错误输入、工具失败和检索为空。

这一天我理解到，eval 不是为了证明项目完美，而是为了暴露问题。如果测试全是简单题，成功率看起来很高，但意义不大。真正有价值的测试，应该覆盖项目容易失败的地方。

我还开始记录失败类型。比如是工具调用错、检索错、输出格式错，还是模型自己编了。只有把失败分类，后续才知道应该改 prompt、改工具、改 RAG，还是改异常处理。

Day 41 的关键结论是：好的 eval 不是让 Agent 显得很强，而是帮我找到它哪里还不稳。

## Day 42：失败处理与稳定性

第四十二天我重点做失败处理。

前面项目能跑起来，但能跑和稳定是不一样的。真实使用里，用户可能输入不完整，工具可能失败，网络可能超时，模型可能输出格式错误，RAG 可能检索不到内容。

如果这些情况都没有处理，项目就只是 demo。稳定的 Agent 不是永远不出错，而是出错时能给出合理反馈，并且尽量恢复。

比如工具失败时告诉用户稍后重试，检索为空时说明没有找到相关资料，模型格式错误时尝试重新解析或重新请求，用户输入不完整时主动追问。

Day 42 的关键结论是：失败处理让 Agent 从实验脚本更接近真实产品。稳定性不是没有错误，而是错误不会直接毁掉体验。

## Day 43：Demo 脚本与录屏准备

第四十三天我开始准备 Demo。

前面一直在写功能、调架构、补评估。今天我意识到，能做出来是一回事，能讲清楚又是另一回事。一个好的 Demo 不是把所有功能都展示一遍，而是用一个清楚场景，让别人快速理解项目价值。

Demo 需要回答几个问题：你解决了什么问题，用户怎么使用，Agent 做了哪些关键动作，结果有什么价值，背后有什么技术亮点。

这一天我理解到，Demo 需要叙事。如果只是点来点去，观众很难记住。如果先讲问题，再演示解决过程，理解就会顺很多。

Day 43 的关键结论是：Demo 不是功能清单，而是一次有节奏的展示。讲清楚价值，比展示所有细节更重要。

## Day 44：技术博客

第四十四天我写毕业项目技术博客。

这篇文章不是简单记录我做了什么，而是要把项目讲清楚。它应该包括为什么做这个项目、用户场景是什么、架构怎么设计、核心模块怎么实现、遇到了哪些问题、eval 结果怎么样、下一步怎么改进。

这一天我理解到，写技术博客是对项目的二次理解。有些东西写代码时觉得自己懂了，但一写文章就发现说不清楚。说不清楚的地方，往往就是理解还不够扎实的地方。

技术博客不是包装，而是复盘。它能帮助我把零散代码、设计选择和踩坑经验整理成一条完整逻辑。

Day 44 的关键结论是：技术博客是把项目从“我做过”变成“我讲得清楚”。

## Day 45：最终作品集交付

第四十五天是 45 天学习计划的最后一天。

这一天我没有继续加新功能，而是整理最终作品集。45 天里，我从 token、attention、Transformer 基础开始，慢慢走到 messages、tool use、RAG、ReAct、memory、多 Agent、工程化和毕业项目。

一开始我只是觉得 AI 很神秘。现在至少能把它拆成几个层次：模型如何处理文本，Agent 如何组织消息，工具如何被调用，知识如何被检索，记忆如何保存，系统如何评估，项目如何展示。

最终作品集不应该只是代码，还应该包括学习笔记、实验代码、Agent 项目、eval 结果、Demo 脚本、技术博客和复盘总结。这些东西加在一起，才说明这 45 天不是只看教程，而是真的做了一遍。

Day 45 的关键结论是：45 天的目标不是学完 AI，而是建立一个能继续生长的 Agent 学习系统。
