## Day 13：System Prompt 工程

大家好，今天是我学习 AI Agent 的第十三天。

前两天我理解了 messages 和上下文管理。今天我继续往下学 system prompt。

以前我以为 prompt 就是给模型一句指令，比如“帮我总结一下”。但今天我发现，system prompt 更像是给 Agent 定底层规则。

user message 是这一次要做什么，system message 更像是这个助手长期要遵守什么。

比如它是谁，回答要严谨还是简洁，能不能编造信息，输出要不要固定格式，遇到不确定的问题要怎么处理。

今天我最大的收获是：system prompt 不是写得越长越好，而是要清楚地定义边界。

一个好的 system prompt，应该让模型知道三件事：

第一，它扮演什么角色。  
第二，它必须遵守什么约束。  
第三，它应该用什么格式输出。

如果 system prompt 写得模糊，模型就容易自由发挥。  
如果写得太啰嗦，反而会浪费 token，也可能冲淡重点。

所以 Day 13 我给自己的总结是：

**System prompt 是 Agent 的行为底盘。它决定模型不是单纯回答问题，而是按某种规则持续工作。**

今天最重要的三句话是：

第一，system prompt 定规则，user prompt 给任务。  
第二，好的 prompt 要明确角色、约束和输出格式。  
第三，prompt 工程不是堆字数，而是减少歧义。

## Day 14：Few-Shot 与推理提示

大家好，今天是我学习 AI Agent 的第十四天。

今天我学的是 few-shot 和推理提示。

以前我给模型提要求，喜欢直接写规则。比如告诉它“请按这个格式输出”。但今天我发现，有时候给模型讲十条规则，不如直接给它两个例子。

这就是 few-shot。

few-shot 的意思是：在正式任务前，先给模型几个输入和输出的样例。

模型会从例子里学到格式、语气、判断标准和边界。

比如我想让模型做分类，与其只说“请判断情绪”，不如给它几个例子：

这句话是积极。  
这句话是消极。  
这句话是中性。

然后再让它处理新句子。

今天我最大的收获是：模型很擅长模仿模式。

规则告诉它应该怎么做，例子让它看到具体怎么做。

我也学到，推理提示不是所有场景都要用。对于复杂问题，可以引导模型先分析再回答。对于简单抽取和固定格式任务，过多推理反而可能增加冗余。

Day 14 的总结是：

**Few-shot 的本质，是用例子降低模型理解任务的成本。**

今天最重要的三句话是：

第一，例子往往比抽象规则更稳定。  
第二，few-shot 适合分类、抽取、格式化输出。  
第三，推理提示要看任务复杂度，不是越多越好。

## Day 15：Function Calling 入门

大家好，今天是我学习 AI Agent 的第十五天。

今天我第一次认真理解 function calling，也就是工具调用。

以前我以为 Agent 会自己去查天气、发邮件、算数据。今天我才明白，模型本身并不会真的执行这些动作。

它做的是另一件事：判断什么时候应该调用哪个工具，并生成一段结构化参数。

比如用户问：“上海天气怎么样？”

模型不会自己访问天气网站。它会说：我需要调用 `get_weather` 这个工具，参数是 `city=上海`。

真正执行工具的是我们的程序。

这让我对 Agent 的本质有了更清楚的理解：

**Agent = 模型判断 + 程序执行 + 结果回传。**

Function calling 里最重要的是 schema。

schema 会告诉模型：工具叫什么，能做什么，需要哪些参数，参数是什么类型。

如果 schema 写得含糊，模型就容易选错工具，或者传错参数。

所以 Day 15 的总结是：

**模型不是自己动手做事，而是学会提出“我要调用哪个工具”。**

今天最重要的三句话是：

第一，function calling 是让模型选择工具，不是让模型亲自执行工具。  
第二，工具 schema 决定模型能不能正确理解工具。  
第三，Agent 的行动能力来自外部程序，而不是模型本体。

## Day 16：Tool Runtime

大家好，今天是我学习 AI Agent 的第十六天。

昨天我学了 function calling，知道模型会提出要调用哪个工具。今天我学的是 tool runtime，也就是工具执行器。

如果说 function calling 是模型“举手说我要用工具”，那 tool runtime 就是程序真正把这个工具跑起来。

今天我理解了一个完整链路：

用户提出问题。  
模型判断需要调用工具。  
模型输出工具名和参数。  
程序检查参数。  
程序执行本地函数或 API。  
工具结果再回到模型上下文。  
模型根据结果给最终回答。

这条链路看起来简单，但里面有很多工程细节。

比如工具名不存在怎么办？参数缺失怎么办？工具执行失败怎么办？返回结果太长怎么办？

今天我最大的收获是：Agent 要稳定，不能只依赖模型聪明，还要靠程序兜底。

工具执行器必须做参数校验、错误处理和结果压缩。

否则一个小错误就可能让整个 Agent 中断。

Day 16 的总结是：

**Tool runtime 是 Agent 从“会说”到“会做”的桥。**

今天最重要的三句话是：

第一，模型负责选择工具，程序负责执行工具。  
第二，工具执行器要处理参数、错误和返回结果。  
第三，Agent 的稳定性，很大一部分来自工程兜底。

## Day 17：RAG 索引

大家好，今天是我学习 AI Agent 的第十七天。

今天我开始正式进入 RAG。

前面我已经学过 embedding，知道文本可以变成语义向量。今天我把这个能力用到文档检索里。

RAG 的第一步，不是直接问模型，而是先处理资料。

我们要把一篇篇文档切成小块，也就是 chunk。然后给每个 chunk 生成 embedding，存进索引里。

这样用户提问时，系统就可以先找到和问题最相关的文档片段。

今天我最大的收获是：chunk 切得好不好，会直接影响 RAG 效果。

如果 chunk 太大，里面会混进很多无关内容。  
如果 chunk 太小，语义可能不完整。  
如果没有重叠，关键信息可能刚好被切断。

所以 RAG 不是简单地“把文档塞给模型”。

它更像是先整理资料库，再让模型按需取资料。

Day 17 的总结是：

**RAG 的第一步是把知识变成可检索的结构。**

今天最重要的三句话是：

第一，文档要先切块，再做 embedding。  
第二，chunk 策略会影响检索质量。  
第三，RAG 不是让模型记住资料，而是让系统能找回资料。

## Day 18：RAG 问答链路

大家好，今天是我学习 AI Agent 的第十八天。

昨天我做了 RAG 索引，今天我把检索和回答连起来。

完整流程是：

用户提问。  
问题变成 embedding。  
系统去索引里找最相关的 chunk。  
把这些 chunk 放进 prompt。  
模型基于这些资料回答。

这让我更清楚地理解了 RAG 的本质：

**不是模型自己知道答案，而是先把相关资料找出来，再让模型阅读资料后回答。**

今天我也意识到，RAG 不等于不会幻觉。

如果检索错了，模型可能基于错误资料回答。  
如果资料不够，模型可能补充猜测。  
如果 prompt 没有限制，模型可能不引用来源。

所以 RAG 问答里很重要的一点是：要求模型基于检索内容回答，不知道就说不知道。

今天我最大的收获是：RAG 的质量不只取决于模型，也取决于检索。

Day 18 的总结是：

**RAG 是“先找资料，再生成回答”，检索质量决定回答上限。**

今天最重要的三句话是：

第一，RAG 回答前必须先 retrieve。  
第二，模型回答应该基于检索片段。  
第三，检索错了，生成再强也可能错。

## Day 19：ReAct Loop

大家好，今天是我学习 AI Agent 的第十九天。

今天我学的是 ReAct。

ReAct 是 Reasoning 和 Acting 的结合，也就是边思考边行动。

以前我理解 Agent，觉得它就是一次调用模型，然后拿到答案。今天我发现，真正的 Agent 往往是一个循环。

它会先想：我下一步要做什么？  
然后行动：调用工具。  
然后观察：拿到工具结果。  
再继续想：现在够不够回答？要不要再调用别的工具？

这个循环就是：

Thought。  
Action。  
Observation。  
再 Thought。

今天我最大的收获是：Agent 的自主性不是魔法，而是循环。

模型每一步只做一个小决策。程序负责执行动作，并把结果放回上下文。这样多轮下来，就像 Agent 会自己推进任务。

但 ReAct 也有风险。

如果没有最大步数，可能一直循环。  
如果工具结果不清楚，可能走偏。  
如果输出格式不稳定，程序就解析失败。

所以 ReAct 既需要提示词，也需要工程约束。

Day 19 的总结是：

**Agent 的自主性，来自模型决策、工具执行和观察结果之间的循环。**

今天最重要的三句话是：

第一，ReAct 是边想边做。  
第二，Thought、Action、Observation 构成 Agent 循环。  
第三，循环必须有边界，否则 Agent 容易失控。

## Day 20：Memory

大家好，今天是我学习 AI Agent 的第二十天。

今天我学的是记忆机制。

之前我已经知道，模型的“记忆感”很多时候来自 messages。只要历史消息还在上下文里，模型就能参考它。

但上下文窗口有限，不能无限塞历史。

所以 Agent 需要更明确的 memory 设计。

今天我把记忆分成几类。

第一种是短期记忆。  
比如当前对话最近几轮内容。

第二种是长期记忆。  
比如用户偏好、长期事实、稳定信息。

第三种是向量记忆。  
把大量资料或历史片段变成 embedding，需要时再检索回来。

今天我最大的收获是：记忆不是越多越好。

如果 Agent 什么都记，就会把临时信息当成长期偏好。  
如果记忆不更新，就会保留过时信息。  
如果记忆不加筛选，就会污染上下文。

所以好的记忆机制，应该有写入规则、读取规则和删除规则。

Day 20 的总结是：

**Agent 的记忆不是简单保存聊天记录，而是有选择地保留有长期价值的信息。**

今天最重要的三句话是：

第一，短期记忆服务当前对话。  
第二，长期记忆保存稳定偏好和事实。  
第三，记忆需要筛选，否则会变成噪音。

## Day 21：Agent Eval 初版

大家好，今天是我学习 AI Agent 的第二十一天。

今天我学的是 eval，也就是评估。

以前我判断一个 Agent 好不好，主要靠感觉。跑几个例子，觉得回答不错，就以为它能用了。

今天我发现，这种方式很不可靠。

Agent 需要一组固定测试用例。

比如十个问题，每个问题都有预期行为。然后每次改 prompt、改工具、改代码，都重新跑一遍。

这样才能知道：这次修改是真的变好了，还是只是碰巧某个例子变好了。

今天我学到几个基本指标：

成功率。  
延迟。  
token 成本。  
工具调用是否正确。  
输出格式是否稳定。  
幻觉或失败类型。

今天我最大的收获是：没有 eval，就很难做 Agent 工程。

因为 Agent 的行为会受 prompt、模型、工具、上下文影响。只靠人工感觉，很容易漏掉问题。

Day 21 的总结是：

**Eval 是让 Agent 从“看起来能用”变成“可以被验证”的关键。**

今天最重要的三句话是：

第一，Agent 不能只靠感觉评估。  
第二，固定测试集可以帮助比较改动前后效果。  
第三，成功率、成本、延迟和失败类型都要记录。

## Day 22：个人助理 Agent v1 整合

大家好，今天是我学习 AI Agent 的第二十二天。

今天我做的是阶段二整合。

前面我分别学了 messages、上下文管理、system prompt、few-shot、tool use、RAG、ReAct、memory 和 eval。

今天的任务，是把这些东西串成一个个人助理 Agent v1。

这个过程让我意识到，单个概念学懂是一回事，把它们接起来又是另一回事。

一个 Agent 不是只有模型。

它有输入消息，有上下文管理，有工具注册，有工具执行，有检索，有记忆，还有评估。

每一块单独看都不复杂，但组合起来就需要清楚的结构。

今天我最大的收获是：Agent 工程的难点，不是某一个函数，而是各模块之间的边界。

比如：

工具结果应该在哪里压缩？  
记忆应该什么时候写入？  
RAG 检索结果应该放进哪段 prompt？  
eval 应该测最终答案，还是也测工具调用过程？

这些都是工程问题。

Day 22 的总结是：

**个人助理 Agent v1 是把模型能力、工具能力、知识检索和记忆机制接成一个可运行系统。**

今天最重要的三句话是：

第一，Agent 是多个模块的组合，不只是一个 prompt。  
第二，模块边界越清楚，后面越容易迭代。  
第三，v1 不求完美，先跑通闭环最重要。

## Day 23：Orchestrator-Worker 架构

大家好，今天是我学习 AI Agent 的第二十三天。

今天我开始进入多 Agent 架构。

第一个学的是 Orchestrator-Worker，也就是主控和执行者模式。

可以把 Orchestrator 理解成项目经理。  
它负责理解目标、拆分任务、分配任务、汇总结果。

Worker 则像执行人员。  
每个 worker 负责一个更具体的子任务。

今天我最大的收获是：多 Agent 不是为了显得高级，而是为了解决复杂任务的拆分问题。

如果一个任务很简单，一个 Agent 就够了。  
如果任务很复杂，需要研究、写代码、测试、总结，多 Agent 才有意义。

但多 Agent 也不是免费午餐。

它会增加 token 成本。  
增加延迟。  
增加协调复杂度。  
还可能出现信息传递错误。

所以今天我学到一个很重要的判断：

**不是能拆就拆，而是拆分带来的收益要大于沟通成本。**

Day 23 的总结是：

**Orchestrator-Worker 架构适合复杂任务，但前提是任务真的需要分工。**

今天最重要的三句话是：

第一，Orchestrator 负责规划和协调。  
第二，Worker 负责具体执行。  
第三，多 Agent 的价值来自分工，不来自数量。

## Day 24：Subagent 设计原则

大家好，今天是我学习 AI Agent 的第二十四天。

昨天我学了 Orchestrator-Worker，今天继续思考一个问题：什么时候应该创建 subagent？

一开始我觉得，只要任务复杂，就可以多拆几个 Agent。

但今天我发现，这样很容易过度设计。

Subagent 有几个适合的场景。

第一，任务可以清楚拆分。  
比如研究、编码、测试、写总结。

第二，不同子任务需要不同上下文。  
比如一个 Agent 专门看文档，另一个 Agent 专门改代码。

第三，需要权限隔离。  
比如有的 Agent 只能读文件，有的 Agent 可以执行操作。

第四，可以并行处理。  
这样才可能节省时间。

如果这些条件都不满足，强行拆分只会增加沟通成本。

今天我最大的收获是：Subagent 不是角色扮演，而是工程边界。

每个 subagent 都应该有清楚的输入、输出和责任范围。

Day 24 的总结是：

**创建 subagent 前，先问它是否真的能降低复杂度，而不是增加复杂度。**

今天最重要的三句话是：

第一，subagent 要有明确职责。  
第二，拆分会带来沟通成本。  
第三，好的拆分让系统更清楚，坏的拆分让系统更混乱。

## Day 25：Skill Registry

大家好，今天是我学习 AI Agent 的第二十五天。

今天我学的是 Skill Registry。

如果说工具是一个个具体能力，那 Skill Registry 就像一本能力目录。

它告诉 Agent：系统里有哪些技能，每个技能能做什么，需要什么输入，会返回什么输出。

以前我写工具，可能只是把函数放在那里。今天我意识到，对 Agent 来说，工具本身不够，工具描述也很重要。

因为模型要根据描述来选择技能。

如果描述写得含糊，模型就可能选错。  
如果输入输出不清楚，执行阶段就容易出错。

所以 Skill Registry 的重点不是“有多少技能”，而是每个技能能不能被正确理解和调用。

今天我最大的收获是：技能注册表是 Agent 的工具箱目录。

人使用工具箱时，需要知道锤子是干嘛的，螺丝刀是干嘛的。Agent 也一样。

Day 25 的总结是：

**Skill Registry 让 Agent 从一堆工具里，选择最合适的能力。**

今天最重要的三句话是：

第一，技能不仅要存在，还要被描述清楚。  
第二，name、description、input、output 都很重要。  
第三，技能路由的质量，取决于注册表的清晰度。

## Day 26：感知-推理-执行三层架构

大家好，今天是我学习 AI Agent 的第二十六天。

今天我学的是感知、推理、执行三层架构。

这个架构让我对 Agent 产品化有了更清楚的理解。

感知层负责输入。  
比如用户消息、文件、网页、数据库、工具返回结果。

推理层负责判断。  
比如理解目标、拆分任务、选择工具、判断风险。

执行层负责行动。  
比如调用 API、写文件、运行代码、发送请求。

以前我看 Agent，容易把所有东西混在一起。今天用三层结构一拆，就清楚很多。

一个 Agent 出问题，也可以按层排查。

输入是不是没读对？  
推理是不是判断错了？  
执行是不是工具失败了？

今天我最大的收获是：三层架构让 Agent 不再是一团 prompt，而是一个系统。

Day 26 的总结是：

**感知负责看见，推理负责决定，执行负责行动。**

今天最重要的三句话是：

第一，感知层处理输入。  
第二，推理层做决策。  
第三，执行层完成动作并返回结果。

## Day 27：LangGraph 入门

大家好，今天是我学习 AI Agent 的第二十七天。

今天我开始学习 LangGraph。

前面我手写过 ReAct loop，知道 Agent 可以通过循环推进任务。LangGraph 则是把这个过程变成图。

图里面有几个核心概念：

state。  
node。  
edge。

state 是当前任务的状态。  
node 是一个处理步骤。  
edge 是步骤之间怎么流转。

今天我最大的收获是：LangGraph 的重点不是“框架很高级”，而是它让 Agent 流程更可控。

手写 loop 的时候，流程容易藏在代码里。  
用 graph 后，流程会更明确。

比如：

Day 27 的总结是：

Day 32 的总结是：

**Vibe Coding 不是把方向交给 AI，而是人定方向，AI 加速实现，人持续校准。**
